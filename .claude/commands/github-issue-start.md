# GitHub Issue 생성 + 작업 시작 (합본)

유저가 준 짧은 설명을 기반으로 팀의 이슈 템플릿(bug/task)을 자동으로 골라 제목·본문·라벨을 채워 `gh`로 이슈를 만들고, 그 이슈에 맞는 작업 브랜치를 `origin/<parent>`에서 따서 바로 체크아웃합니다. **승인 게이트 없이 끝까지 직진**하며, 진짜 에러(미설치/인증 만료/원격 부재/충돌)일 때만 멈춥니다.

## 동작 순서

각 단계의 **의도**를 이해하고 이상 신호가 보이면 정지하세요. 사용자 확인은 받지 않습니다 — 이 커맨드를 호출했다는 것 자체가 "내가 준 설명으로 이슈 만들고 바로 작업 들어가달라"는 의미입니다.

### 1. 컨텍스트 수집

병렬로 읽어옵니다.

- `git remote get-url origin` — GitHub 저장소 식별 (owner/repo)
- `.github/ISSUE_TEMPLATE/bug-template.md`, `.github/ISSUE_TEMPLATE/task-template.md` — 섹션 구조가 바뀌어 있을 수 있으니 실제 파일로 확인
- `git branch --show-current` — 이전 브랜치 (보고에 사용)
- `git status --porcelain` — 워킹 트리 상태 (체크아웃 단계의 사전 신호)
- `git fetch origin` — 부모 브랜치를 최신 상태로 끌어와야 거기서 새 브랜치를 딸 수 있음

### 2. 템플릿 타입 판정

유저 입력의 맥락으로 `bug` / `task` 중 하나를 고릅니다.

| 템플릿 | 판정 힌트 |
|---|---|
| `bug` | 기존 동작이 깨짐, 에러/예외/스택트레이스·로그 언급, "안 돼요", "작동하지 않음", 재현 조건이 나옴 |
| `task` | 신규 기능, 개선, 리팩토링, 문서 작업, 설정 추가, "~ 구현/추가/개선" |

판단이 애매하면 **`task`로 디폴트**합니다 (개발 작업의 다수가 task). 묻지 않습니다.

### 3. 작업 타입 & 라벨 결정

한국어 Conventional Commits용 `type`을 고르고, `type` → 라벨로 매핑합니다. 템플릿과 느슨하게 연결되지만 1:1은 아닙니다 (예: bug 템플릿이라도 긴급도에 따라 `fix`/`hotfix`가 갈림).

| 상황                | type | 라벨 |
|-------------------|---|---|
| 새 기능/엔드포인트/엔티티 추가 | `feat` | `feat` |
| 버그 수정             | `fix` | `bug` |
| 프로덕션 장애성 긴급 수정    | `hotfix` | `bug` |
| 빌드/의존성/설정/초기 세팅   | `chore` | `chore` |
| 문서만 변경            | `docs` | `docs` |
| 코드 구조 변경/개선       | `refactor` | `refactor` |
| 테스트만 추가/수정        | `test` | `refactor` |

여기서 정한 `type`은 단계 6에서 브랜치명 만들 때 그대로 재사용합니다 (제목을 다시 파싱하지 않습니다).

매핑된 라벨이 저장소에 없으면 `gh issue create --label`이 실패합니다. 이 경우 `--label`을 **생략해 이슈를 먼저 만들고**, 최종 보고에 "라벨 미부착(저장소에 없음)"으로 명시합니다. 현재 저장소 라벨은 `gh label list`로 확인 가능. (자동으로 라벨을 새로 만들지는 않습니다 — 라벨 관리 책임은 사용자에게.)

### 4. 제목 작성

한국어 Conventional Commits — `<type>: <한국어 요약>` (예: `feat: 사용자 JWT 인증 추가`, `fix: 로그인 시 500 에러 수정`).

- 70자 이내
- 유저 입력에 포함된 구체적 대상(파일/기능/엔드포인트)을 그대로 반영
- 외삽으로 범위를 과도하게 확장하지 말 것. 모르는 건 본문에 "미확인"으로 남기세요.

### 5. 본문 작성

선택한 템플릿을 **그대로 복제**해서 각 섹션을 채웁니다. 섹션 제목(이모지 포함)과 순서는 원본과 정확히 일치시키세요.

- 유저 입력에서 **직접 추론 가능한 내용만** 채웁니다.
- 값을 모르는 섹션(버그의 정확한 로그·스택트레이스, Given-When-Then의 구체 조건 등)은 템플릿의 안내 blockquote(`>`)를 **원본 그대로 남기고 본문은 비워두세요**. 유저가 나중에 채우도록.
- 유저가 재현 단계/기대 결과를 줬다면 Given-When-Then으로 정리. 없는 걸 지어내지 말 것.
- 태스크의 `## ✅작업 상세 내용`은 설명에서 뽑아낸 하위 작업을 `- [ ]` 3~5개로 정리. 정말 불명확하면 `- [ ] TODO` 한 줄만 두세요.

### 6. 이슈 생성

```bash
gh issue create \
  --title "<title>" \
  --label <label> \
  --body "$(cat <<'EOF'
<body 전체>
EOF
)"
```

- 라벨이 매핑 대상이 없거나 저장소에 없으면 `--label` 플래그를 생략
- 생성된 이슈 번호와 URL을 보관 (다음 단계와 최종 보고에 사용)

### 7. 브랜치명·부모 브랜치 결정

**브랜치명**: `<type>/#<이슈번호>-<desc>` (예: `feat/#12-jwt-auth`, `fix/#7-login-500-fix`).

- `type`은 단계 3에서 정한 값을 그대로 씀 (제목 재파싱 없음).
- `desc`는 제목에서 접두사·콜론을 걷어낸 부분을 영문 kebab-case(소문자, `-` 구분)로 30자 내 요약. 한글은 번역하거나 핵심 영단어만 추출 (예: "로그인 500 에러 수정" → `login-500-fix`, "JWT 인증 추가" → `jwt-auth`).
- 선행 0 패딩 없음 — 이슈 번호를 그대로 (`1` → `1`, `9` → `9`, `10` → `10`). `chore/#2-init-claude-skill` 컨벤션에 맞춤.

**부모 브랜치**:

| type | 부모 브랜치 |
|---|---|
| `feat`, `fix`, `chore`, `docs`, `refactor`, `test` | `origin/dev` |
| `hotfix` | `origin/prod` |

해당 부모 브랜치가 원격에 없으면 멈추고 사용자에게 실제 부모 브랜치를 확인합니다 (이슈는 이미 생성된 상태이므로 이슈 URL을 함께 알리세요).

### 8. 브랜치 생성 + 체크아웃

```bash
git switch --no-track -c "<type>/#<num>-<desc>" "origin/<parent>"
```

- `git switch -c`는 브랜치 생성과 체크아웃을 한 번에 수행하고, 동일 이름이 이미 있으면 실패합니다 (안전).
- **`--no-track` 필수, 그리고 `-c`보다 앞에 와야 함** (`-c`가 뒤에 오는 토큰을 브랜치명으로 먹어버려서 순서가 뒤집히면 "only one reference expected"로 실패). 이 플래그가 없으면 git은 기본으로 `origin/<parent>`를 upstream으로 잡아버리고, 이후 무심코 `git push`/`git pull` 하면 부모 브랜치로 푸시를 시도하거나 부모 변경을 끌어오는 사고가 납니다. upstream은 PR 만들 시점에 `/github-pr`이 `git push -u origin <branch>`로 올바르게 설정합니다.
- 원격 푸시는 하지 않습니다 — PR 만들 시점에 `/github-pr`이 자연스럽게 푸시합니다.
- **워킹 트리가 더러워서 git switch가 실패**하면 정지하고, 이슈 URL과 만들려던 브랜치명을 보고한 뒤 사용자가 커밋/스태시 후 수동으로 같은 명령을 다시 실행하도록 안내하세요.
- **동일 이름 브랜치가 이미 존재**해서 실패하면(같은 이슈 번호+desc 조합 재실행 등) 정지하고 사용자에게 알린 뒤 처리 방법을 묻습니다: 기존 브랜치로 체크아웃만(`git switch <name>`) / 다른 `desc`로 재생성 / 기존 브랜치 삭제 후 재생성.

### 9. 결과 보고

- 생성된 이슈 URL
- 부착된 라벨 (없으면 "없음 — 저장소에 매핑 라벨이 없어 생략")
- 이전 브랜치 → 현재 브랜치
- 이슈 번호 (PR 본문에서 `Closes #<번호>`로 쓰일 값)
- 다음 단계 안내: 작업 후 커밋 → `/github-pr`로 PR 생성

## 실패 시 대응

- `gh` 미설치 → `brew install gh && gh auth login` 안내
- 인증 만료 → `gh auth status`로 확인 후 재로그인 안내
- 이슈 템플릿 파일이 없거나 섹션 구조가 바뀜 → 정지하고 사용자에게 최신 템플릿 확인 요청
- 매핑된 라벨이 저장소에 없음 → `--label` 생략해 이슈 먼저 생성, 최종 보고에 명시
- 부모 브랜치가 원격에 없음 → 정지, 이슈는 이미 생성됐다고 알리고 실제 부모 브랜치 확인
- `git switch` 실패 (워킹 트리 더러움 / 브랜치명 충돌) → 정지, 이슈 URL과 브랜치명을 보고하고 위의 단계 8 가이드대로 수동 처리 유도
