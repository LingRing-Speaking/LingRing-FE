# GitHub Issue 자동 생성

유저가 준 짧은 설명을 기반으로 팀의 이슈 템플릿(bug/task)을 자동으로 선택해 제목·본문을 채우고, `gh`로 이슈를 생성합니다. 브랜치 생성은 이 커맨드의 책임이 아닙니다 — 실제로 그 이슈 작업을 시작할 때 `/github-issue-start`로 따로 처리합니다.

## 동작 순서

각 단계의 **의도**를 이해하고 이상이 보이면 사용자에게 확인을 요청하세요. 이슈는 생성 즉시 외부에 노출되고 편집 이력이 남으므로, 제목/본문/라벨을 **생성 직전에 한 번 보여주고 승인받은 뒤** 진행하세요.

### 1. 컨텍스트 수집

병렬로 읽어옵니다.

- `git remote get-url origin` — GitHub 저장소 식별 (owner/repo)
- `.github/ISSUE_TEMPLATE/bug-template.md`, `.github/ISSUE_TEMPLATE/task-template.md` — 섹션 구조가 바뀌어 있을 수 있으니 실제 파일로 확인

### 2. 템플릿 타입 판정

유저 입력의 맥락으로 `bug` / `task` 중 하나를 고릅니다. 애매하면 묻습니다.

| 템플릿 | 판정 힌트 |
|---|---|
| `bug` | 기존 동작이 깨짐, 에러/예외/스택트레이스·로그 언급, "안 돼요", "작동하지 않음", 재현 조건이 나옴 |
| `task` | 신규 기능, 개선, 리팩토링, 문서 작업, 설정 추가, "~ 구현/추가/개선" |

입력이 너무 짧아 판단이 서지 않으면 **유저에게 확인**하세요. 잘못된 템플릿으로 생성하면 편집 비용이 큽니다.

### 3. 작업 타입 & 라벨 결정

한국어 Conventional Commits용 `type`을 고르고, `type` → 라벨로 매핑합니다. 템플릿과 느슨하게 연결되지만 1:1은 아닙니다 (예: bug 템플릿이라도 긴급도에 따라 `fix`/`hotfix`가 갈림).

| 상황                | type | 라벨 |
|-------------------|---|---|
| 새 기능/엔드포인트/엔티티 추가 | `feat` | `feat` |
| 버그 수정             | `fix` | `bug` |
| 프로덕션 장애성 긴급 수정    | `hotfix` | `bug` |
| 빌드/의존성/설정/초기 세팅   | `chore` | `chore` |
| 문서만 변경            | `docs` | `docs` |
| 코드 구조 변경/개선       | `refactor` | `refactor` |
| 테스트만 추가/수정        | `test` | `refactor` |

매핑된 라벨이 저장소에 존재하지 않으면 `gh issue create --label`이 실패합니다. 이 경우 `--label`을 생략해 이슈를 먼저 만들고, **라벨 누락을 사용자에게 알린 뒤** 필요하면 `gh label create`로 생성 후 `gh issue edit --add-label`로 부착하세요. 현재 저장소 라벨은 `gh label list`로 확인할 수 있습니다.

이슈 제목에 찍힌 `type`은 `/github-issue-start`가 나중에 브랜치 타입을 결정할 때 재사용합니다. **제목 접두사와 라벨의 작업 타입은 일관되게 유지**하세요.

### 4. 제목 작성

한국어 Conventional Commits — `<type>: <한국어 요약>` (예: `feat: 사용자 JWT 인증 추가`, `fix: 로그인 시 500 에러 수정`).

- 70자 이내
- 유저 입력에 포함된 구체적 대상(파일/기능/엔드포인트)을 그대로 반영
- 외삽으로 범위를 과도하게 확장하지 말 것. 모르는 건 본문에 "미확인"으로 남기세요.

### 5. 본문 작성

선택한 템플릿을 **그대로 복제**해서 각 섹션을 채웁니다. 섹션 제목(이모지 포함)과 순서는 원본과 정확히 일치시키세요.

- 유저 입력에서 **직접 추론 가능한 내용만** 채웁니다.
- 값을 모르는 섹션(버그의 정확한 로그·스택트레이스, Given-When-Then의 구체 조건 등)은 템플릿의 안내 blockquote(`>`)를 **원본 그대로 남기고 본문은 비워두세요**. 유저가 나중에 채우도록.
- 유저가 재현 단계/기대 결과를 줬다면 Given-When-Then으로 정리. 없는 걸 지어내지 말 것.
- 태스크의 `## ✅작업 상세 내용`은 설명에서 뽑아낸 하위 작업을 `- [ ]` 3~5개로 정리. 정말 불명확하면 `- [ ] TODO` 한 줄만 두세요.

### 6. 사용자 승인

여기서 멈춥니다. 아래를 한 블록에 모아 보여주고 확인을 받으세요.

- 템플릿 타입: bug / task
- 제목
- 라벨
- 본문 전체 미리보기

"이대로 진행할까요?" 식으로 물어보고, 승인 전에는 **이슈를 생성하지 않습니다**. 수정 요청이 오면 반영 후 다시 승인을 받으세요.

### 7. 이슈 생성

```bash
gh issue create \
  --title "<title>" \
  --label <label> \
  --body "$(cat <<'EOF'
<body 전체>
EOF
)"
```

- 라벨이 매핑 대상이 없거나 저장소에 없으면 `--label` 플래그를 생략

### 8. 결과 보고

- 이슈 URL
- 부착된 라벨 (없으면 "없음")
- 다음 단계 안내: 이 이슈로 작업을 시작할 때 `/github-issue-start`를 실행하면 브랜치 생성·체크아웃까지 자동으로 된다는 한 줄

## 실패 시 대응

- `gh` 미설치 → `brew install gh && gh auth login` 안내
- 인증 만료 → `gh auth status`로 확인 후 재로그인 안내
- 매핑된 라벨이 저장소에 없음 → `--label` 생략해 이슈 먼저 생성, 사용자에게 알림 (필요 시 `gh label create` → `gh issue edit --add-label`)
- 템플릿 파일이 없거나 섹션 구조가 바뀜 → 멈추고 사용자에게 최신 템플릿을 확인받은 뒤 진행
